# WarmHouse

# Задание 1. Анализ и планирование

### 1. Описание функциональности монолитного приложения

**Управление отоплением:**

- Пользователи могут удалённо включать/выключать отопление в доме;
- Пользователи не могут самостоятельно подключаться к системе — только специалист по подключению;
- Система поддерживает управление отоплением через синхронные запросы от сервера к системе отопления;
- Система поддерживает регистрацию датчиков в системе при их включении.

**Мониторинг температуры:**

- Пользователи могут просматривать состояние датчиков и текущую температуру в домах через web-интерфейс;
- Пользователи не могут самостоятельно подключать свои датчики к системе;
- Система поддерживает сбор информации для мониторинга температуры через синхронные запросы от сервера к датчикам;
- Система поддерживает регистрацию датчиков в системе при их включении.

### 2. Анализ архитектуры монолитного приложения

**Язык программирования:** Go
**База данных:** PostgreSQL
**Архитектура:** Монолитная, все компоненты системы (обработка запросов, бизнес-логика, работа с данными) находятся в рамках одного приложения.
**Взаимодействие:** Синхронное, запросы обрабатываются последовательно.
**Масштабируемость:** Ограничена, так как монолит сложно масштабировать по частям.
**Развертывание:** Требует остановки всего приложения.

### 3. Определение доменов и границы контекстов

**AS IS:**
- Домен: Управление отоплением
  - Контекст: Подключение и отключение устройств
  - Контекст: Установка температуры
  - Контекст: Хранение информации об устройствах
- Домен: Данные устройств
  - Контекст: Получение текущей температуры
  - Контекст: Хранение информации о текущей температуре

**TO BE:**

- Домен: Управление пользователями
  - Контекст: Регистрация пользователей, аутентификация и авторизация в системе
  - Контекст: Хранение данных пользователя

- Домен: Управление датчиками и модулями устройств умного дома
  - Поддомен: Управление модулями управления отоплением:
    - Контекст: Подключение к модулям управления отоплением (отправка команд выключения/выключения и установки температуры, получение телеметрии).
    - Контекст: Хранение информации о подключенных устройствах отопления.
  - Поддомен: Управление модулями управления светом:
    - Контекст: Подключение к модулям управления светом (отправка команд включения/выключения, установка параметров освещения, получение телеметрии).
    - Контекст: Хранение информации о подключенных устройствах освещения.
  - Поддомен: Управление модулями управления воротами:
    - Контекст: Подключение к модулям управления воротами (отправка команд открытия/закрытия, получение телеметрии).
    - Контекст: Хранение информации о подключенных устройствах управления воротами.
  - Поддомен: Управление модулями видеонаблюдения:
    - Контекст: Подключение к модулям видеонаблюдения (отправка команд, получение телеметрии, фото/видео-стриминг);
    - Контекст: Хранение информации о подключенных устройствах видеонаблюдения;
    - Контекст: Хранение истории видеонаблюдения.
  - Поддомен: Управление универсальными модулями:
    - Контекст: Подключение к универсальным модулям (отправка команд, сбор телеметрии);
    - Контекст: Хранение информации о подключенных универсальных устройствах.

- Домен: Управление устройствами пользователей
  - Контекст: Управление устройствами пользователя, просмотр состояния устройств;
  - Контекст: Автоматизация сценариев управления устройствами пользователей
  - Контекст: Управление устройствами пользователя, просмотр состояния устройств;  

- Домен: Телеметрия устройств пользователя
  - Контекст: Асинхронное получение и обработка потока телеметрии устройств
  - Контекст: Обработка потока показателей устройства и предоставление информации о телеметрии
  - Контекст: Хранение телеметрии устройств

### 4. Проблемы монолитного решения

- невозможно масштабировать разные компоненты системы;
- сложность обавление новых функци;
- обновления требуют остановки всего приложения;
- ошибка в одном из компонентов может привести к неработоспособности всего приложения;
- отсутствие возможности самостоятельного подключения устройств;

# Задание 4. Создание и документирование API

### 1. Тип API

При построении системы использовалось 2 типа взаимодействия микросервисов: синхронный и асинхронный.
Синхронное взаимодействие через HTTP-API использовалось для создания, изменения, удаления сущностей системы, отправки команд устройствам и модулям, получения информации о сущностях.
Асинхронное взаимодействие через брокер сообщений использовалось для обработки потока телеметрии от подключенных модулей. Такое решение позволит обеспечить буферизацию данных и масштабироваться при росте потока данных.
В качестве варианта решения можно было рассмотреть событийную архитектуру взаимодействия микросервисов. Но такое решение накладывает дополнительные требования к формализации структуры событий и организации надёжного транспорта. Мне показалось, что для текущего состава команды разработчиков это может быть лишней нагрузкой. Но в перспективе разбиение системы на микросервисы позволит при необходимости постепенно внедрить такой подход.
