# WarmHouse

# Задание 1. Анализ и планирование

### 1. Описание функциональности монолитного приложения

**Управление отоплением:**

- Пользователи могут удалённо включать/выключать отопление в доме;
- Пользователи не могут самостоятельно подключаться к системе — только специалист по подключению;
- Система поддерживает управление отоплением через синхронные запросы от сервера к системе отопления;
- Система поддерживает регистрацию датчиков в системе при их включении.

**Мониторинг температуры:**

- Пользователи могут просматривать состояние датчиков и текущую температуру в домах через web-интерфейс;
- Пользователи не могут самостоятельно подключать свои датчики к системе;
- Система поддерживает сбор информации для мониторинга температуры через синхронные запросы от сервера к датчикам;
- Система поддерживает регистрацию датчиков в системе при их включении.

### 2. Анализ архитектуры монолитного приложения

**Язык программирования:** Go
**База данных:** PostgreSQL
**Архитектура:** Монолитная, все компоненты системы (обработка запросов, бизнес-логика, работа с данными) находятся в рамках одного приложения.
**Взаимодействие:** Синхронное, запросы обрабатываются последовательно.
**Масштабируемость:** Ограничена, так как монолит сложно масштабировать по частям.
**Развертывание:** Требует остановки всего приложения.

### 3. Определение доменов и границы контекстов

**AS IS:**
- Домен: Управление устройствами
  - Контекст: Подключение и отключение устройств
  - Контекст: Установка температуры
  - Контекст: Хранение информации об устройствах
- Домен: Данные устройств
  - Контекст: Получение текущей температуры
  - Контекст: Хранение информации о текущей температуре

**TO BE:**

- Домен: Пользовательские интерфейсы
  - Контекст: Регистрация пользователей и управление профилем
  - Контекст: Аутентификация и авторизация в системе
  - Контекст: Хранение данных пользователя
  - Контекст: Web-приложение для работы пользователей в системе
  - Контекст: Мобильное приложение для работы пользователей
  - Контекст: Личный кабинет для управления устройствами пользователя, просмотр дашбордов телеметрии, управления сценариями работы устройств

- Домен: Управление устройствами
  - Поддомен: Устройства пользователя
    - Контекст: Подключение и отключение устройств различных типов, предоставление информации о подключенных устройствах
    - Контекст: Хранение информации о подключенных устройствах пользователя
  
  - Поддомен: Взаимодействие с устройствами
    - Контекст: Приём команд включения/выключения и установки значений параметров устройств
    - Контекст: Организация асинхронной доставки команд устройству
    - Контекст: Передача команды включения/выключения, а так же установки параметров отопления устройству
    - Контекст: Сбор и получение телеметрии устройства отопления
    - Контекст: Кэширование параметров подключения к устройствам
  
- Домен: Управление сценариями пользователя
  - Поддомен: Создание сценариев
    - Контекст: Создание, удаление и управление активностью сценария, предоставление информации о сценариях пользователя
    - Контекст: Настройка workflow выполнения сценария
    - Контекст: Хранение данных о сценариях и настройках их workflow
  
  - Поддомен: Выполнение сценариев
    - Контекст: Генерация триггеров для запуска сценариев (команды пользователя, телементрия устройств)
    - Контекст: Асинхронное получение потока телеметрии для запуска триггеров по условию
    - Контекст: Выполнение workflow сценария
    - Контекст: Хранение состояния запущенных процессов, хранение параметров триггеров активных сценариев

- Домен: Телеметрия устройств пользователя
  - Контекст: Асинхронное получение потока телеметрии устройств
  - Контекст: Обработка потока показателей устройства
  - Контекст: Организация хранения телеметрии устройств
  - Контекст: Предоставление различной информации о телеметрии в различных срезах

### 4. Проблемы монолитного решения

- невозможно масштабировать разные компоненты системы;
- обновления требуют остановки всего приложения;
- ошибка в одном из компонентов может привести к неработоспособности всего приложения;

# Задание 5. Работа с docker и docker-compose

Перейдите в apps.

Там находится приложение-монолит для работы с датчиками температуры. В README.md описано как запустить решение.

Вам нужно:

1) сделать простое приложение temperature-api на любом удобном для вас языке программирования, которое при запросе /temperature?location= будет отдавать рандомное значение температуры.

Locations - название комнаты, sensorId - идентификатор названия комнаты

```
	// If no location is provided, use a default based on sensor ID
	if location == "" {
		switch sensorID {
		case "1":
			location = "Living Room"
		case "2":
			location = "Bedroom"
		case "3":
			location = "Kitchen"
		default:
			location = "Unknown"
		}
	}

	// If no sensor ID is provided, generate one based on location
	if sensorID == "" {
		switch location {
		case "Living Room":
			sensorID = "1"
		case "Bedroom":
			sensorID = "2"
		case "Kitchen":
			sensorID = "3"
		default:
			sensorID = "0"
		}
	}
```

2) Приложение следует упаковать в Docker и добавить в docker-compose. Порт по умолчанию должен быть 8081

3) Кроме того для smart_home приложения требуется база данных - добавьте в docker-compose файл настройки для запуска postgres с указанием скрипта инициализации ./smart_home/init.sql

Для проверки можно использовать Postman коллекцию smarthome-api.postman_collection.json и вызвать:

- Create Sensor
- Get All Sensors
